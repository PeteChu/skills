How sync-engine fits together

Prompt I'm picking up the sync engine next sprint and have never opened it. Draw me the shape of it: which modules exist, how they connect, where a single keystroke actually goes, and where I should start reading.

The package turns local edits into an append-only operation log, persists them to IndexedDB, and streams them to the server over one socket. Everything flows through Session: it is the only module that touches both storage and the network, so it is the one file worth reading end to end.

03

One keystroke, hop by hop

The numbers match the clay arrows. Steps 1–3 are synchronous with the keystroke; 4–6 happen whenever the socket is free.

  1. 1

    react/useDocument.ts :31–44

    The editor's onChange converts the ProseMirror step into an Op and calls session.apply(op). The hook re-renders from the change event, never from its own state.

  2. 2

    session.ts :58–91 the hub

    This is the function to understand. apply stamps the op with a hybrid logical clock, appends it to the log, applies it to the in-memory doc, and enqueues it for sending, in that order. If the append throws, nothing else happens.

    source 
    // packages/sync-engine/src/session.ts
async apply(op: LocalOp): Promise<void> {
  const stamped = { ...op, ts: this.clock.now(), actor: this.actorId };
  await this.log.append(stamped);        // 3 · durable first
  this.doc = applyOp(this.doc, stamped);
  this.emit('change', this.doc);
  this.outbox.enqueue(stamped);           // 4 · fire and forget
}
  3. 3

    oplog/OpLog.ts :22–40 → storage/idb.ts :15

    OpLog.append batches writes into one IndexedDB transaction per animation frame. The await resolves when the batch commits, which is where most of the 1.8 ms goes.

    source 
    // packages/sync-engine/src/oplog/OpLog.ts
append(op: StampedOp): Promise<void> {
  this.pending.push(op);
  this.flushing ??= nextFrame().then(() => {
    const batch = this.pending.splice(0);
    this.flushing = null;
    return this.store.putMany('ops', batch);
  });
  return this.flushing;
}
  4. 4

    outbox.ts :18–52

    The outbox coalesces adjacent text inserts (typing "hello" becomes one op, not five) and keeps at most one batch in flight. Unacked ops stay in IndexedDB, so a crash re-sends them on the next boot.

  5. 5

    transport/socket.ts :40–77

    Messages are posted to the SyncWorker port, which owns the real socket. Reconnect uses 0.5 s → 30 s backoff and replays everything after the last acked clock value.

  6. 6

    rebase/rebase.ts :9–120

    The server ack carries any remote ops that landed first. rebase() transforms the still-pending local ops over them and tells Session to emit a fresh doc. This is the least-tested file in the package.

    source 
    // packages/sync-engine/src/rebase/rebase.ts
export function rebase(pending: StampedOp[], remote: StampedOp[]) {
  let out = pending;
  for (const r of remote) {
    out = out.map((p) => transform(p, r, p.ts < r.ts ? 'left' : 'right'));
  }
  return out.filter((p) => !isNoop(p));  // deletes of deleted text vanish
}

Gotchas

  • The doc updates after the IndexedDB commit. A slow disk shows up as typing lag, not as a sync delay.
  • Safari private mode has no IndexedDB. IdbStore silently falls back to memory, so notes vanish on reload.
  • The tie-break in rebase() compares clock values with <. Equal stamps from two actors fall to 'right' on both sides, which is only safe because actor is folded into ts.

Boundaries

  • ✓Only session.ts imports both storage and transport.
  • ✓rebase/ and clock/ are pure: no I/O, no timers.
  • ✕react/ reaches into oplog/ once (debug panel). Lint rule pending.
