02

Data flow

Saving a schedule is a plain write. Everything interesting happens later, on the scheduler path (clay), which runs without a user present.

Clay = runs unattended and must be idempotent. Gray = request/response or fire-and-forget.

03

Decisions you might want to change

I made two judgment calls. Toggle either one to see the alternative. The migration in section 05 and the hand-off summary at the bottom follow your choice.

Choice ① · timing

When is the invoice created?

PLAN’S PICK · draft 3 days ahead

The tick creates a draft at period_start − 3d and finalizes it on the due date. Owners can fix a line item before it goes out.

Cost: a second state transition (draft → open) and a "review upcoming" list in the UI. Adds about ½ day.

ALTERNATIVE · generate at due time

The tick creates and sends the invoice on the due date in one step. That gives one fewer state and no new UI list.

Pick this if your customers rarely edit recurring invoices. Mistakes then need a credit note instead of an edit.

Choice ② · data model

How is the repeat rule stored?

PLAN’S PICK · explicit columns

interval_unit, interval_count, anchor_day. This covers weekly, monthly, quarterly, and yearly, which is every request in the support backlog. It is queryable and has a check constraint.

Cost: "2nd Tuesday of the month" needs a migration later.

ALTERNATIVE · RRULE string

One rrule text column (RFC 5545), parsed with the rrule package. It handles any calendar pattern.

Pick this if you expect calendar-style rules soon. It adds a dependency, cannot be queried in SQL, and needs about 1 extra day for validation and editor UX.

05

Key code

These are the two pieces most likely to be done wrong: the schema, where the rule shape follows choice ②, and the idempotent tick.

packages/billing-core/migrations/0057_recurring.sql · RRULE variant

create table invoice_schedules (
  id            uuid primary key,
  account_id    uuid not null references accounts,
  template_id   uuid not null references invoices,
  interval_unit  text check (interval_unit in
                 ('week','month','year')),
  interval_count int  not null default 1,
  anchor_day     int  check (anchor_day between 1 and 31),
  rrule          text not null, -- 'FREQ=MONTHLY;BYMONTHDAY=1'
  timezone      text not null,  -- account tz, not UTC
  next_run_at   timestamptz not null,
  ends_after    int,             -- null = never
  paused_at     timestamptz
);

create table schedule_runs (
  schedule_id   uuid references invoice_schedules,
  period_start  date not null,
  invoice_id    uuid references invoices,
  primary key (schedule_id, period_start)
);

services/scheduler/src/jobs/recurringTick.ts

export async function recurringTick(db: Db, now = new Date()) {
  const due = await db.claimDueSchedules({
    before: addDays(now, 3)now, limit: 200,
  }); // FOR UPDATE SKIP LOCKED

  for (const s of due) {
    const period = nextPeriod(s, s.timezone);
    await db.tx(async (tx) => {
      const run = await tx.insertRun(s.id, period.start)
        .onConflictDoNothing();
      if (!run) return;   // another tick won
      const inv = await generateInvoice(tx, s, period, {
        status: 'draft''open',
      });
      await tx.advance(s.id, period.next);
    });
  }
}

Risks & mitigations

RiskSevMitigation
Two scheduler pods overlap and bill the same period twice.HIGHPrimary key on (schedule_id, period_start) plus SKIP LOCKED. A test runs two ticks concurrently against the real database.
Anchor day 31 in February, or 29 in a non-leap year.MEDClamp to the last day of the month inside nextPeriod(). Table-driven tests cover all 12 months × days 28–31.
Invoice dated the wrong day for accounts far from UTC.MEDStore the account timezone on the schedule and compute periods in local time. Never derive the date from now() in SQL.
The template invoice is edited mid-cycle, so future invoices change silently.LOWShow "affects the next invoice on 1 Dec" on save. The draft window (choice ①) gives a second chance.
