#904: Stream build logs over SSE instead of polling

Prompt Write up PR #904 for reviewers. Explain why we're doing it, show before vs. after, walk through each file with the why, and tell them exactly where to focus. Priya and Sam haven't touched the log pipeline since it was built.

TL;DR

The build page polled GET /builds/:id/log?after=N every 2 s. A log line could take up to 2 s to appear, and at peak 600 open tabs generated 18k Postgres reads a minute. This PR pushes lines over Server-Sent Events fed by Redis pub/sub. Lines arrive in about 140 ms, and database reads drop by about 93%. Polling stays as an automatic fallback.

01

Why

Polling was fine when builds were short and few people watched them. Two things changed: the monorepo's test stage now prints for 11 minutes, and release days put 600 people on build pages at once. Each tab asks "anything new?" 30 times a minute, and the answer is usually no.

Before

  • Browser polls every 2 s with setInterval
  • Every poll is a Postgres range read on log_chunks
  • Lines appear 0–2 s late, in bursts
  • Background tabs keep polling (throttled to 1/min by the browser)

After

  • One EventSource per tab, server pushes lines
  • Runner publishes chunks to Redis, and the stream fans them out
  • Postgres is read once on connect (backfill), then never
  • Reconnects resume from Last-Event-ID with no gaps or dupes

02

File by file

The files are in reading order, not alphabetical. Start with the new endpoint, then the producer that feeds it, then the client. Tests and infra come last.

services/logs/src/stream.ts new +94

The heart of the PR. On connect it backfills from Postgres starting at Last-Event-ID, then subscribes to build:{id}:log in Redis. Each event's id is the byte offset, so the browser's built-in reconnect resumes exactly where it stopped. A 15 s heartbeat keeps the ALB from closing idle streams.

router.get('/builds/:id/log/stream', async (req, res) => {
  res.writeHead(200, SSE_HEADERS);           // incl. X-Accel-Buffering: no
  let offset = Number(req.get('Last-Event-ID') ?? 0);

  // subscribe FIRST, buffer, then backfill: no gap between the two
  const sub = await pubsub.subscribe(`build:${req.params.id}:log`);
  for (const c of await readChunks(req.params.id, offset)) offset = send(res, c);
  sub.on('chunk', (c) => { if (c.end > offset) offset = send(res, c); });

  const beat = setInterval(() => res.write(': ping\n\n'), 15_000);
  req.on('close', () => { clearInterval(beat); sub.close(); });
});
services/runner/src/logSink.ts mod +18 −6

The producer. After a chunk is committed to log_chunks, the sink publishes it. Publishing after commit means a subscriber can never see a line that a later backfill wouldn't also return. I also removed the 500 ms batching timer. It existed to make polling cheaper and now only adds latency.

  this.timer = setInterval(() => this.flush(), 500);
  async write(chunk: Chunk) {
    await db.log_chunks.insert(chunk);
    await redis.publish(`build:${chunk.buildId}:log`, encode(chunk));
  }
apps/web/src/hooks/useBuildLog.ts mod +41 −58

The setInterval loop and its after=N bookkeeping are gone. The hook opens an EventSource, appends by offset, and ignores any chunk at or below the last offset it has, so duplicate delivery is harmless. After 3 failed reconnects in 30 s it falls back to the old poller (kept as pollBuildLog()), and it says so in the log header.

The server tests run against real Redis and Postgres (testcontainers). They include the race I was most worried about: a chunk published during backfill must appear exactly once. The client tests use a fake EventSource to drive reconnect with Last-Event-ID and the fallback to polling.

03

Where to focus your review

  1. 1

    Subscribe-then-backfill ordering

    stream.ts:6–8. If these two lines are swapped, a chunk published between the backfill read and the subscribe is lost forever. The c.end > offset check is what makes the overlap safe. Please convince yourself it can't drop or duplicate a line.

  2. 2

    Connection count per pod

    Each tab now holds one open connection and one Redis subscription. At about 150 per pod we're far from Node's limits, but each subscription costs a Redis client. I share one subscriber per pod and fan out in memory (pubsub.ts, unchanged). Sanity-check that assumption against the Redis maxclients of 10k.

  3. 3

    What I deliberately did not do

    No WebSockets, because we only need server → client. No log search or ANSI parsing changes. I did not delete the poller, which stays for one release as the fallback. Each of these is a clean follow-up, and bundling them would make this PR hard to review.
