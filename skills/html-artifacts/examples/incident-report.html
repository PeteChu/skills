Post-incident review · INC-2026-1027 · acme-shop

Inventory consumer stalled; storefront oversold 1,842 orders

SEV-2 Resolved Customer impact 37 min Detected Oct 27 · 14:26 UTC IC Lena Vogel
Prompt Write up Tuesday's oversell incident from #inc-1027, the consumer logs and the deploy history. Blameless, minute by minute, and end with action items that have owners.

TL;DR

A deploy of inventory-consumer raised max_poll_records from 100 to 2,000 while the batched-upsert code path it depended on was still flagged off in production. Each poll then took ~320 s, longer than Kafka's 300 s poll limit, so consumers were evicted and rebalanced in a loop. Stock counts froze for 37 minutes and the storefront kept selling items that were already gone. We stopped the oversell with the inventory.strict_reserve flag, rolled back, and drained the backlog. No stock data was lost.

03

Root cause

PR #3127 had two halves: a new batched upsert in stock/writer.go, guarded by inventory.batch_upserts, and a config bump so each poll returns enough records to batch. The flag was on in staging and the load test, but off in production. The config shipped with the deploy; the flag did not.

With the flag off, each record still costs one round-trip (~160 ms under afternoon load). 2,000 records × 160 ms ≈ 320 s, which is longer than the 300 s max.poll.interval.ms. Kafka treats the consumer as dead, revokes its partitions, and the rebalance hands the same oversized batch to the next consumer. Nothing commits, so nothing progresses.

deploy/inventory-consumer/values-prod.yaml · PR #3127

@@ -14,7 +14,7 @@ consumer:
14 group_id: inventory-sync
15 auto_offset_reset: earliest
16− max_poll_records: 100
16+ max_poll_records: 2000 # pairs with inventory.batch_upserts
17 max_poll_interval_ms: 300000
18 session_timeout_ms: 45000

Contributing factors

  • The lag alert needs 50k for 10 minutes. Lag passed 50k at ~14:16, so the page could not fire before 14:26.
  • The storefront trusts the Redis stock cache with no staleness check. A frozen cache looks exactly like a healthy one.
  • The canary's 2% traffic never produced a full batch, so it could not reproduce the timeout.

05

What went well, what didn't

Went well

  • The strict_reserve kill switch existed, was documented in the runbook and stopped the bleeding in one click.
  • Kafka retention meant zero stock events were lost; replay was automatic after rollback.
  • Support escalated within 15 minutes with concrete order IDs.

Didn't go well

  • Customers noticed before monitoring did.
  • The deploy annotation was not on the lag dashboard, so the 13:58 change was not obvious for 12 minutes.
  • Config that depends on a flag shipped without checking the flag's prod state.
