  2. 09:40
    Discovery

    Tenant identity only exists after authn.Middleware

    Registered the limiter between authn and proxy.Handler in cmd/gateway/router.go:58. Unauthenticated routes such as /v1/auth/token are already IP-limited in nginx, so I left them alone.

  3. 10:05
    Deviation 1 of 4

    API-key tokens carry org_id, not tenant_id

    Plan said
    Key buckets by the tenant_id JWT claim.
    Code revealed
    Tokens minted in authn/apikey.go only set org_id. That was 31% of yesterday's traffic. Their tenant_id is "", so they would all have shared one bucket.
    Conservative call
    Resolve org → tenant with the existing tenants.ResolveOrg() (LRU, 5 min TTL). If that fails, apply the lowest tier (20 rps) under rl:unresolved:<org_id>. Never use a shared bucket.
    Revisit
    Should unresolved orgs fail open instead? That's a product call. Logged for you.
  4. 10:48
    As planned

    Step 3: 429 with Retry-After and X-RateLimit-* headers

    The body uses the problem+json shape from docs/api/errors.md, with type: rate_limited. Contract tests updated in api/contract/errors_test.go.

  5. 11:20
    Deviation 2 of 4

    Failing closed on Redis errors would turn a blip into an outage

    Plan said
    If Redis is unreachable, reject with 429 to protect upstreams.
    Code revealed
    The limiter shares redis.Shared with sessions, and internal/sessions already fails open after 50 ms. Failing closed here would make every Redis hiccup a full API outage, which is stricter than the behavior we already accept.
    Conservative call
    Fall back to an in-process bucket per pod sized limit ÷ 6 (HPA minReplicas). Redis timeout is 30 ms. Count fallbacks in ratelimit_degraded_total.
    Revisit
    At 20 pods the effective limit is 3.3× the configured one. That's fine for minutes, not for hours. Alert after 5 min degraded.

  7. 13:05
    Deviation 3 of 4

    Limits already live in plan entitlements, so I dropped the new table

    Plan said
    Add a tenant_limits table (migration 0093) and admin CRUD.

  8. 13:40

    Step 7: metrics and the "Gateway / Rate limits" dashboard

  9. 14:22
    Deviation 4 of 4

    Webhook ingress is exempt, in shadow mode

    Plan said
    Every route behind the gateway is limited.
    Code revealed
    /hooks/stripe and /hooks/github are called by providers that back off exponentially on 429. Stripe backs off for up to 3 days, so a burst limit would delay invoice.paid events.
    Conservative call
    Exempt /hooks/* and /healthz through the route allowlist. Record them as decision="shadow" so we can see what would have been limited.
    Revisit
    Provider IP ranges are published. A generous per-provider bucket may be better than a blanket exemption.

What this changes about attempt #2

Paste these into the next plan or prompt so the next run starts from today's surprises instead of rediscovering them.

  1. Name the identity resolver, not the claim. Callers arrive with tenant_id (user JWTs) or only org_id (API keys, 31% of traffic). The plan should say to use tenants.ResolveOrg() and what happens when it fails.
  2. State the failure policy relative to neighbors. Shared Redis already fails open for sessions. Any new Redis consumer needs its fail-open or fail-closed choice and per-pod fallback sizing written down before the build.
  3. Search for the existing source of truth before adding a table. plans.yaml entitlements already held limits. Add a "prior art" step to the plan template.
  4. List inbound callers that aren't users. Webhook providers react badly to 429s. Decide exemptions or provider-specific buckets up front.
