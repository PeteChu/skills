Bloom filters, one bit array at a time

Prompt Our crawler keeps re-crawling URLs it has already seen, and someone said "just put a Bloom filter in front of it." I don't know what that is. Teach me enough to understand the tradeoffs and to ask you for the right thing.

The crawler has seen about 100 million URLs. Keeping them all in a hash set costs gigabytes. A Bloom filter answers "have I seen this?" in about 120 MB, at the price of sometimes saying yes when the honest answer is no. It never makes the opposite mistake. That asymmetry is the whole idea, and it happens to suit a crawler: a wrong "yes" skips one page, a wrong "no" would re-crawl one.

01

The mental model

A row of bits, all starting at 0, and a few hash functions. That's the entire data structure.

  1. 1 · Add

    Run the URL through k hash functions. Each gives a position in the bit array. Set those k bits to 1.

  2. 2 · Ask

    Hash the URL the same way and look at the same k bits. You never store the URL itself.

  3. 3 · Answer

    Any bit is 0 → definitely not seen. All are 1 → probably seen, unless other URLs set them: a false positive.

04

Words for your next prompt

Each rung: the term, what it means in one breath, and how you'd say it to an engineer (or to me).

False-positive rate p

The fraction of never-seen items the filter wrongly calls "seen". You pick it up front; everything else follows from it.

"Size the filter for 100 M URLs at a 0.5% false-positive rate."

Bits per item m / n

Memory budget per element. About 9.6 bits gives 1%, 14.4 gives 0.1%. It doesn't depend on how long the URLs are.

"We can afford 12 bits per item. What false-positive rate does that buy?"

Optimal k

The number of hashes that minimizes false positives: (m/n)·ln 2. Too few under-uses the array; too many fills it up faster.

"Derive k from m/n rather than hard-coding 3."

Double hashing

Instead of k independent hash functions, compute two and combine them: h₁ + i·h₂. Same accuracy, far cheaper. This page does it.

"Use Kirsch–Mitzenmacher double hashing off one 128-bit xxHash."

Saturation

When more items go in than planned, the fill ratio climbs and the FP rate rises sharply. Nothing errors; it just quietly degrades.

"Alert when fill ratio passes 50% so we rebuild before the FP rate drifts."

Scalable / counting variants

Scalable chains bigger filters as you grow. Counting swaps bits for small counters so you can delete, at ~4× the memory.

"We never delete, so plain Bloom is enough; plan for growth with a scalable filter."

05

What good looks like for the crawler

  • ✓Normalize before hashing. acme.dev/Blog/ and acme.dev/blog must hash the same, or the filter is useless.
  • ✓The cost of a false positive is known. A skipped page. At 1% that's ~400 of 40k new URLs a day; decide if that's acceptable.
  • ✓Sized for next year, not today. Plan n at 2× current volume, or use a scalable filter.
  • ✓Persisted and reloadable. The bit array is a plain byte buffer; snapshot it with the crawl state.
  • !Not the source of truth. Re-crawl decisions that matter (e.g. "has this page changed") still go to the database.

Glossary · hover a dotted term

Bit array m
A fixed row of m bits, all 0 at the start. The only thing the filter stores.
Hash functions k
Each maps an item to one bit position. Same item, same positions, every time.
False positive
"Probably seen" for an item never added, because others set all its bits.
Fill ratio
Share of bits set to 1. At the optimal k it settles near 50%.
Counting filter
Small counters instead of bits, so items can be removed.
Scalable filter
A chain of filters, each larger and stricter, added as the set grows.
