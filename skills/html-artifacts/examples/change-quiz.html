The mental model

Deleting a project used to be one irreversible step. Now it is a lifecycle with two new states and a 30-day window.

02

Three non-obvious behaviors

You won't get these from skimming the diff. Each one is deliberate, and each one will come up in a support ticket.

B1

A default scope hides trashed projects everywhere, including from Project.find

What
default_scope { where(deleted_at: nil) } means every existing query skips trashed rows, and Project.find(id) raises RecordNotFound for them. Admin and restore code must use Project.with_deleted.
Why
There are 140+ call sites that load projects. A scope hides trashed rows from all of them without touching each one. The cost: background jobs enqueued before the delete now raise, and ApplicationJob's discard_on ActiveRecord::RecordNotFound silently drops them.
Where
app/models/project.rb:8 app/controllers/trash_controller.rb:21 app/jobs/application_job.rb:4
B2

Trashing a project frees its slug, so restore can collide

What
The unique index on (workspace_id, slug) is now partial: WHERE deleted_at IS NULL. Someone can create a new project with a trashed project's slug. Restoring the old one then returns 409 slug_taken, and the UI asks for a new slug.
Why
Holding slugs for 30 days blocked the common "delete and recreate" flow in usability testing. A collision on restore is rarer and easy to explain.
Where
db/migrate/20261028_partial_slug_index.rb app/services/projects/restore.rb:34
B3

Purge deletes attachments first, rows last, and is safe to rerun

What
The nightly job sets purge_started_at, deletes S3 attachments, then deletes the row. If S3 times out halfway, the row stays and the job picks it up again the next night. Once purge_started_at is set, restore returns 410 Gone.
Why
The row is the retry handle. If the row were deleted first, a failure would leave orphaned files with nothing pointing at them. A project may therefore sit in trash for 31+ days, but it is never half-restorable.
Where
app/jobs/purge_trashed_projects_job.rb:15 config/schedule.yml:42

Existing behavior this leans on

Search visibility depends on the after_commit :reindex callback. Trashing uses update!(deleted_at: Time.current), which fires the callback, and SearchIndexer drops the project's tasks from results. Anything that uses update_all or update_column skips callbacks and leaves trashed tasks searchable. The planned bulk-trash ticket BRD-877 does exactly that.
