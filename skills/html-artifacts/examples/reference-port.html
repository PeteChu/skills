01

What the library actually does

  • Parses five fields (parse.py): lists, inclusive ranges, steps, month and day names. Sunday may be written 0 or 7.
  • Day-of-month and day-of-week are OR'd when both are restricted, and AND'd when either is *. Whether a field "is star" is decided from the text, not the expanded set (Vixie cron behavior).
  • Evaluates in the job's IANA zone, in wall-clock time (tz.py). A wall time that falls in a DST gap fires at the first valid minute after the gap; a wall time that occurs twice fires once, on the first occurrence.
  • next_fire(after) is strictly after, truncates seconds, and searches at most 5 years before raising NoNextFire (so 0 0 30 2 * fails fast instead of looping).
  • It never runs jobs. It only answers "when next?". Locking, retries and missed-run catch-up stay in src/scheduler/runner.ts, unchanged by this port.

1Three weekday conventions. Python weekday() is Mon=0, isoweekday() is Mon=1…Sun=7, JS getDay() is Sun=0. recur uses isoweekday() % 7; Luxon's weekday is also Mon=1…Sun=7, so the same % 7 carries over exactly.
2"Star" is syntactic. dom_star is set only when the field text is literally * (or ?). 1-31 expands to every day but is not star. The port must carry the flag from the parser, not compute dom.size === 31.

4Ambiguous times: first occurrence. fold=0 picks the earlier (pre-transition) offset, so 02:30 on fall-back day fires once, in summer time. The port relies on Luxon doing the same and pins it with recur's test vector test_fall_back_fires_once rather than trusting the default.

function expand(field: string, lo: number, hi: number) {
  const out = new Set<number>();
  for (const part of field.split(',')) {
    const [rng, stepStr] = part.split('/');
    let [a, b] = rng === '*' ? [lo, hi] : bounds(rng);
    if (stepStr && !rng.includes('-') && rng !== '*') b = hi;7
    const step = stepStr === undefined ? 1 : Number(stepStr);
    if (!(step >= 1)) throw new CronSyntaxError(part);
    for (let v = a; v <= b; v += step) out.add(v);8
  }
  if (hi === 7 && out.delete(7)) out.add(0);9
  return out;
}
75/15 means 5-59/15. A bare start with a step runs to the field's max. Some cron dialects reject this syntax; recur accepts it, 3 live schedules use it, so the port accepts it too.
8Inclusive end, and step 0. range(a, b + 1) includes b, hence <=. Python's range raises on step 0 (surfaced as a syntax error); a JS loop with step 0 spins forever. The explicit guard also rejects NaN from */x.
9Sunday is 0 and 7. Folding 7 into 0 after expansion means 5-7 (Fri–Sun) works. Set.delete returns whether it removed, which keeps the TS a single line.
03

Preserved, deliberately changed, dropped

Preserved exactly

  • DOM/DOW OR rule, with syntactic star
  • Sunday as 0 or 7; ranges across 7
  • Inclusive ranges; 5/15 = 5-59/15
  • DST gap → first valid minute (03:00)
  • DST overlap → once, first occurrence
  • Strictly after, seconds truncated, 5-year cap

Deliberately changed

  • zoneinfo → Luxon, with DST behavior pinned by tests (notes 4–6)
  • NoNextFire → returns null; the runner already branches on null
  • ValueError → CronSyntaxError with the offending field and column
  • set[int] → Set + sorted array cached per spec for the search

Dropped (not needed)

  • @reboot: meaningless in a hosted scheduler; rejected at parse
  • get_prev(): zero callers (grep across both repos)
  • 6-field seconds mode: behind a flag that is off for all 212 schedules
  • pytz fallback for Python 3.8
