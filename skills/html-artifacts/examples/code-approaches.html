Three ways to retry failed webhook deliveries

Prompt Customers are missing webhooks when their endpoint blips. Show me three ways to add retries to src/webhooks/deliver.ts, with tradeoffs for each.

Context: ~42k deliveries/day · 1.8% fail on first attempt · Postgres 15 already in use · no queue infra today

01Inline retry with backoff

Wrap the existing fetch call in a bounded retry loop.

// src/webhooks/deliver.ts
export async function deliver(hook: Hook, body: Payload) {
  for (let attempt = 0; attempt < 4; attempt++) {
    const res = await signedPost(hook.url, body);
    if (res.ok) return record(hook, 'delivered');
    if (res.status < 500) break;   // 4xx: don't retry
    await sleep(250 * 2 ** attempt + jitter());
  }
  return record(hook, 'failed');
}
Pro
Con
Ten-line change, ships today
Max window is ~2 s, so it misses longer outages
No schema or infra change
Holds the API worker while sleeping
Easy to unit test with fake timers
A deploy mid-retry loses the event
Retry window: ~2 s Durability: none New infra: 0 Effort: ½ day
Recommended

02Postgres outbox + worker

Write deliveries to a table in the same transaction; a worker drains it.

-- migrations/0042_webhook_outbox.sql
create table webhook_outbox (
  id bigserial primary key, hook_id uuid, body jsonb,
  attempts int default 0, next_at timestamptz default now()
);

// src/webhooks/worker.ts — every 2 s
const rows = await db.query(`select * from webhook_outbox
  where next_at <= now() order by next_at
  limit 50 for update skip locked`);
for (const r of rows) await attempt(r); // bumps next_at
Pro
Con
Survives deploys and crashes
New migration and a worker process
Retries for hours on a schedule we own
Table needs pruning (cron or partition)
Uses the database we already run
Polling adds ~2 s latency to every delivery
Retry window: 24 h Durability: transactional New infra: 1 worker Effort: 3 days

03Managed queue + DLQ

Publish to a cloud queue with visibility timeouts and a dead-letter queue.

// src/webhooks/enqueue.ts
await queue.send({
  queueUrl: env.WEBHOOK_QUEUE_URL,
  body: JSON.stringify({ hookId, body }),
});

// infra/queues.tf
redrive_policy = {
  maxReceiveCount     = 8
  deadLetterTargetArn = aws_sqs_queue.webhooks_dlq.arn
}
Pro
Con
Scales far past current volume
First queue in the stack: IAM, Terraform, local dev story
DLQ gives a built-in "give up" bucket
Publish is not transactional with the DB write
No polling, low latency
Backoff is coarse (visibility timeout)
Retry window: ~4 d Durability: at-least-once New infra: 2 queues + IAM Effort: 1–2 wks

Recommendation

Go with approach 02, the Postgres outbox. The failures in last month's support tickets were endpoint outages of 5–40 minutes, which the 2-second inline window cannot cover. The outbox reuses the database and migration tooling acme-relay already runs, and because the row is written in the same transaction as the event, a deploy can no longer drop a delivery.

Consider approach 03 once delivery volume passes roughly 1M/day or a second service needs a queue. At that point the infrastructure cost is shared. Approach 01 is still worth adding as a first fast attempt inside the outbox worker.

When to choose each

01
Stop-gap this week while 02 is built
02
Now: durable, owned, fits current scale
03
Later, when queues are shared platform infra
